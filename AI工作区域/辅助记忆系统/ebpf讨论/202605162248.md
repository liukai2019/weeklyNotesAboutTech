## 我建议你立刻聚焦的 5 类微需求

### 1. 连接级可见性
最容易起步，也最容易讲故事。

可做题目：
- **谁在和谁通信？**
- **某进程在 1 分钟内连接了哪些远端 IP/端口？**
- **短连接风暴是谁造成的？**
- **一个 CLI/daemon 的网络依赖画像是什么？**

最小产出：
- 跟踪 `connect/accept/send/recv` 或相关 tracepoint
- 输出按 `pid/comm/dst_ip/dst_port` 聚合的表
- 附一个 demo：curl / browser / agent-cli

这类需求和 AgentSight 也天然相连，因为 agent 本质上也在发网络请求。AgentSight 的定位就包括对 AI agent 的 TLS/进程行为做系统级观测。([github.com](https://github.com/eunomia-bpf/agentsight?utm_source=openai))

### 2. DNS 观测
比全量 TCP 更容易讲清楚。

可做题目：
- **某个进程到底解析了哪些域名？**
- **哪个 CLI 工具请求前的 DNS 延迟异常？**
- **AI agent 访问了哪些模型/工具/API 域名？**

原因：
- DNS 很适合做“行为画像”
- 和“讲故事”非常搭：  
  “不是看源码，而是先看 agent/程序到底依赖了哪些外部服务”

### 3. TLS/HTTPS 前后的行为关联
这是从 network observability 过渡到 Agent observability 的桥。

可做题目：
- **一次 HTTPS 请求发生前后，该进程触发了哪些文件读写/子进程行为？**
- **某个 agent 发请求前是否先读取 prompt 文件、配置、token？**
- **网络连接建立和本地文件访问能不能关联成一个时间线？**

这正是 AgentSight 这类项目想解决的一部分：系统边界上的相关行为关联，而不是仅靠应用层 SDK。([github.com](https://github.com/eunomia-bpf/agentsight?utm_source=openai))

### 4. 长连接/重试/超时画像
更贴近“工作价值”和“业务讲故事”。

可做题目：
- **某进程是不是在频繁重连某个服务？**
- **连接失败分布是什么？**
- **哪类远端地址导致了最多的 timeout/refused/reset？**

如果你工作环境里有 modem / IMS / SIP / 内网这种约束环境，这类“网络行为画像”非常容易包装成：
- 提效工具
- 排障辅助
- 业务透明化能力

即使不能在生产里真跑，做个内网模拟版也能讲故事。

### 5. “agent/network/file/process”统一时间线

7. Define validation steps.

- Problem
- User
- Why now
- Why eBPF
- MVP
- Data to collect
- Constraints
- Validation
- Risks
- Next steps

- Always mention likely hook points if relevant.

# dns-watch

## Raw idea

Trace DNS queries triggered by a specified process and record:
- timestamp
- pid
- comm
- query name
- response latency

## Why it matters

This is relevant to network observability and also to real work scenarios where:
- DNS success/failure affects follow-up connection success/failure
- different returned IP addresses may lead to different outcomes
- retry/switchover behavior matters
- teammates need a clearer story of network behavior

## Current uncertainty

The requirement is still vague:
- what exactly counts as a DNS query?
- what exactly counts as success/failure?
- do we need returned IP addresses in v0?
- do we track only one process or process tree?
- how should latency be measured?
- should retries be correlated?

## Initial direction

Start with a very small MVP:
- filter by pid or comm
- detect DNS request + response
- extract query name if feasible
- measure elapsed time between request and response
- print events in a readable format

## Potential business connection

Could support story-friendly diagnostics for DNS-related behavior in telecom/internal systems, including:
- successful lookup followed by failed connect
- alternate IP retry
- DNS timing anomalies

````markdown name=docs/sdd/dns-watch-sdd.md
# SDD: dns-watch v0

## 1. Problem statement

Engineers need a simple way to observe DNS queries made by a specified process so they can understand whether DNS lookup behavior contributes to downstream connection success or failure.

## 2. User

Primary users:
- engineers investigating network behavior of a process
- engineers correlating DNS lookup behavior with later TCP connection outcomes
- teammates who need a concise, explainable view of process-level name resolution behavior

## 3. Why now

The current requirement is not fully clear, but DNS behavior is already known to be relevant to real work scenarios. A small MVP can create clarity quickly and reveal what data is truly needed next.

## 4. Why eBPF

eBPF may be a good fit because:
- it can observe process-triggered network activity with low application intrusion
- it may support per-process visibility better than coarse external capture
- it can evolve into richer network observability later

But eBPF should be justified by actual value. If simpler tools can solve the v0 problem, that should be acknowledged.

## 5. MVP

Version 0 should:
- target a specified pid or comm
- observe DNS request and response activity
- record timestamp
- record pid
- record comm
- record query name if feasible
- record latency between request and response
- print a readable event stream

## 6. Non-goals

Version 0 does not need to:
- fully decode every DNS edge case
- support all resolver implementations
- correlate to TCP connect outcomes yet
- support full process tree correlation yet
- provide dashboards or persistent storage
- be upstream-ready

## 7. Candidate extensions

Possible version 1+ additions:
- DNS result code
- returned IP addresses
- correlation with connect() success/failure
- process tree tracking
- retry and alternate IP analysis
- JSON output
- summary statistics

## 8. Acceptance criteria

Version 0 is successful if:
- it can target a known process
- it can show at least some DNS activity from that process
- it can print query name for a basic test case
- it can estimate response latency for a basic test case
- the output is useful enough to explain one concrete example to another engineer

## 9. Open questions

- Should filtering be by pid, comm, or both?
- Should child processes be included?
- What test program should be used for the demo?
- What is the best observation point in WSL2?
- Is DNS parsing best done in kernel or user space?
- How should success/failure be represented?
- Are returned IP addresses required for the first useful version?

## 10. Next step

Use Copilot to refine this into 2-3 MVP options, then choose one minimal implementation path.
````

- connect() 成功/失败

- 时间线关联
