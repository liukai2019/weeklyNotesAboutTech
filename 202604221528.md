# tel-or-sip-uri-to-sip-uri Specification

## Requirements

### Requirement: Normalize tel-based userinfo and ensure user=phone (configurable)
When normalizing tel/sip URIs related to telephone numbers, the system SHALL:
1) place the entire telephone-subscriber portion (including any tel parameters) in the SIP/SIPS userinfo; and
2) ensure the SIP/SIPS URI includes the parameter `user=phone`;
3) only apply (2) when the SIP/SIPS userinfo conforms to tel URI telephone-subscriber syntax, unless a
   configuration override is enabled.

#### Configuration: TelSyntaxStrictMode
- **Name**: `TelSyntaxStrictMode`
- **Type**: boolean
- **Default**: `false`
- **Behavior**:
  - When `true`, userinfo MUST match a tel URI telephone-subscriber syntax before adding `user=phone`.
  - When `false`, userinfo MAY be treated as tel-like if it is plausibly a telephone-subscriber
    (e.g., digits with optional separators, or contains tel parameters like `;ext=` or `;phone-context=`).

#### Scenario: tel → sip with parameters
- **GIVEN** the tel URI `tel:+358-555-1234567;postd=pp22`
- **WHEN** it is converted to a SIP URI with host `foo.com`
- **THEN** the result is `sip:+358-555-1234567;postd=pp22@foo.com;user=phone`

#### Scenario: sip with tel-style userinfo but missing user=phone
- **GIVEN** the SIP URI `sip:+358-555-1234567;postd=pp22@foo.com`
- **WHEN** it is normalized
- **THEN** the result is `sip:+358-555-1234567;postd=pp22@foo.com;user=phone`

#### Scenario: strict mode enabled, userinfo not matching tel syntax
- **GIVEN** the SIP URI `sip:alice@foo.com`
- **AND** `TelSyntaxStrictMode = true`
- **WHEN** it is normalized
- **THEN** the result is unchanged

# tel-or-sip-uri-to-sip-uri Specification

## Objective
Ensure tel-related URIs are normalized to consistent SIP/SIPS behavior in line with RFC 3261 §19.1.6, so telephone semantics are preserved and explicit.

## Interface
**Input**
- `uri`: URI string to be normalized (tel or sip/sips)
- `realm`: host name (required only when input is a tel URI)
- `config` (optional):
  - `TelSyntaxStrictMode` (boolean, default: false)

**Output**
- A normalized SIP/SIPS URI string

## Logic Rules
1) **tel → sip/sips mapping**  
   If input is a tel URI, the output MUST:
   - place the full telephone-subscriber (including tel parameters) into SIP/SIPS userinfo, and
   - include the URI parameter `user=phone`, and
   - use `realm` as the host.

2) **sip/sips normalization**  
   If input is SIP/SIPS and userinfo conforms to tel URI telephone-subscriber syntax, the output MUST include `user=phone`.

3) **Syntax gating (configurable)**  
   If `TelSyntaxStrictMode = true`, rule (2) applies only when userinfo strictly matches tel syntax.  
   If `TelSyntaxStrictMode = false`, rule (2) may also apply to userinfo that plausibly represents a telephone subscriber (e.g., digits with separators or tel parameters).

## Edge Cases
- If input is SIP/SIPS and userinfo does **not** match tel syntax, the output MUST remain unchanged.
- If input is tel URI but `realm` is missing, behavior is implementation-defined (e.g., return error or reject).

## Examples
1) **tel → sip**  
   Input: `tel:+358-555-1234567;postd=pp22`, realm=`foo.com`  
   Output: `sip:+358-555-1234567;postd=pp22@foo.com;user=phone`

2) **sip missing user=phone**  
   Input: `sip:+358-555-1234567;postd=pp22@foo.com`  
   Output: `sip:+358-555-1234567;postd=pp22@foo.com;user=phone`

3) **non‑tel userinfo**  
   Input: `sip:alice@foo.com`  
   Output: unchanged

## Scenarios

### Scenario: tel → sip with parameters (realm used)
- **GIVEN** the tel URI `tel:+358-555-1234567;postd=pp22`
- **AND** `realm = foo.com`
- **WHEN** it is converted to a SIP URI
- **THEN** the result is `sip:+358-555-1234567;postd=pp22@foo.com;user=phone`

### Scenario: sip with tel-style userinfo but missing user=phone
- **GIVEN** the SIP URI `sip:+358-555-1234567;postd=pp22@foo.com`
- **WHEN** it is normalized
- **THEN** the result is `sip:+358-555-1234567;postd=pp22@foo.com;user=phone`

### Scenario: strict mode enabled, userinfo not matching tel syntax
- **GIVEN** the SIP URI `sip:alice@foo.com`
- **AND** `TelSyntaxStrictMode = true`
- **WHEN** it is normalized
- **THEN** the result is unchanged

### Scenario: tolerant mode adds user=phone for plausible tel userinfo
- **GIVEN** the SIP URI `sip:358-555-1234567@foo.com`
- **AND** `TelSyntaxStrictMode = false`
- **WHEN** it is normalized
- **THEN** the result is `sip:358-555-1234567@foo.com;user=phone`

### Scenario: strict mode accepts valid global-number
- **GIVEN** the SIP URI `sip:+12025550123@foo.com`
- **AND** `TelSyntaxStrictMode = true`
- **WHEN** it is normalized
- **THEN** the result is `sip:+12025550123@foo.com;user=phone`

### Scenario: strict mode accepts local-number with phone-context
- **GIVEN** the SIP URI `sip:1234;phone-context=example.com@foo.com`
- **AND** `TelSyntaxStrictMode = true`
- **WHEN** it is normalized
- **THEN** the result is `sip:1234;phone-context=example.com@foo.com;user=phone`

### Scenario: input already has user=phone
- **GIVEN** the SIP URI `sip:+358-555-1234567@foo.com;user=phone`
- **WHEN** it is normalized
- **THEN** the result is unchanged
